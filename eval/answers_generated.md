## Q6 — Kerberoasting in Active Directory

**Question:** How does Kerberoasting work in Active Directory environments and which HTB machines demonstrate it?

**Answer:**

# Kerberoasting in Active Directory

## Mechanism
Kerberoasting is an attack against the Kerberos protocol used in Windows Active Directory environments. The process involves:
1.  **Ticket Request:** An attacker with a valid domain account authenticates to the Key Distribution Center (KDC) and requests a Ticket Granting Service (TGS) ticket for a specific service Principal Name (SPN).
2.  **Encryption:** The DC encrypts the response using the **service user's password hash** (not the requesting user's hash).
3.  **Offline Brute Force:** Instead of sending the encrypted ticket to the service, the attacker captures the TGS ticket and performs an offline brute-force attack to crack the service account's password.
4.  **Pre-authentication Bypass:** Typically, a valid domain account is required to request the TGS. However, if a user account has the flag **"Do not require Kerberos preauthentication"** (`DONT_REQUIRE_PREAUTH`) set, it is possible to Kerberoast other users without any initial credentials. This technique is implemented in `Rubeus` and `GetUserSPNs.py` (via specific GitHub commits). (seen on: htb-active, htb-rebound)

## Tools & Commands
*   **Rubeus:** Used for Kerberoasting and exploiting the `DONT_REQUIRE_PREAUTH` flag to Kerberoast without credentials. (seen on: htb-sizzle, htb-rebound)
*   **GetUserSPNs.py:** Used to request TGS tickets. Can be run locally or via port forwarding. Specific GitHub versions are required to support Kerberoasting via `DONT_REQUIRE_PREAUTH` accounts. (seen on: htb-sizzle, htb-rebound)
*   **Port Forwarding:** Techniques are used to forward port 88 (Kerberos) to the local host to run `GetUserSPNs.py` from an external machine. (seen on: htb-sizzle)

## HTB Machines Demonstrating Kerberoasting

### Recon & Enumeration
*   **htb-search:** Identified a Kerberoastable user by dumping LDAP data using credentials found in a website image. (seen on: htb-search)
*   **htb-sauna:** Used Kerberoast brute force on usernames to identify users, then found one with the `DONT_REQUIRE_PREAUTH` flag to grab the hash without authenticating to the domain. (seen on: htb-sauna)
*   **htb-rebound:** Combined AS-REP-Roasting with Kerberoasting to obtain a crackable hash for a service account. (seen on: htb-rebound)

### Foothold & Lateral Movement
*   **htb-active:** Practiced Kerberoasting against a Windows Domain as a core vulnerability. (seen on: htb-active)
*   **htb-sizzle:** Performed Kerberoasting after gaining local access to port 88, using Rubeus and port forwarding techniques. (seen on: htb-sizzle)
*   **htb-administrator:** Executed a **targeted Kerberoasting attack** by abusing `GenericWrite` permissions over a user. (seen on: htb-administrator)

## Q14 — WinRM / evil-winrm shell access

**Question:** Which HTB machines used WinRM (evil-winrm) for shell access and in what context?

**Answer:**

# WinRM Shell Access Cheatsheet

## Foothold

### Direct Credential Access
*   **Technique:** Use `evil-winrm` to establish a PowerShell shell using valid credentials.
*   **Command:**
    ```bash
    evil-winrm -u <username> -p <password> -i <target_ip_or_hostname>
    ```
*   **Context:**
    *   **Escapetwo:** Used credentials for user `ryan` to access `dc01.sequel.htb`. (seen on: Escapetwo)
    *   **Apt:** Used credentials for `henry.vinson_adm` (admin-level account) to access `htb.local`. (seen on: Apt)
    *   **Freelancer:** Used credentials for `lorra199` to access `freelancer.htb`. (seen on: Freelancer)
    *   **Puppy:** Used credentials for `adam.silver` to access `puppy.htb`. (seen on: Puppy)
    *   **Support:** Used credentials for `support` (member of Remote Management Users) to access `support.htb`. (seen on: Support)
    *   **Cascade:** Used credentials for `s.smith` to access `10.10.10.182` (Windows 2008). (seen on: Cascade)
    *   **Driver:** Used credentials for `tony` to access `10.10.11.106`. (seen on: Driver)

### Post-Exploitation / Privilege Escalation Context
*   **Technique:** Change service account password to gain WinRM access.
*   **Context:**
    *   **Rebound:** Changed the password for the `winrm_svc` account using `bloodyAD` from a compromised account (`oorend`), then used `evil-winrm` to connect to `dc01.rebound.htb`. (seen on: Rebound)

### Verification Tools
*   **Technique:** Verify WinRM access before connecting with `evil-winrm`.
*   **Tools:** `crackmapexec` or `netexec`.
*   **Commands:**
    ```bash
    crackmapexec winrm <target> -u <username> -p <password>
    netexec winrm <target> -u <username> -p <password>
    ```
*   **Context:**
    *   **Puppy:** Verified access for `adam.silver` using `netexec`. (seen on: Puppy)
    *   **Support:** Verified access for `support` using `crackmapexec`. (seen on: Support)
    *   **Cascade:** Verified access for `s.smith` using `crackmapexec`. (seen on: Cascade)
    *   **Rebound:** Verified access for `winrm_svc` using `netexec` after password change. (seen on: Rebound)
    *   **Driver:** Verified access for `tony` using `crackmapexec`. (seen on: Driver)
