# Evaluation Writeup — HTB Cheatsheet Assistant (RAG)

## 1. Executive Summary & Benchmark Setup

This document presents a rigorous quantitative and qualitative evaluation of the **HTB Cheatsheet Assistant**, an offensive security RAG system built over 462 Hack The Box (HTB) writeups. The system is evaluated against a 15-question hand-curated test set comprising:
- **5 Broad "Cheatsheet"-style questions** (Q1–Q5): Requiring broad-corpus synthesis, multi-technique structuring, and cross-machine categorization across the offensive lifecycle.
- **10 Specific "Mechanistic & Target"-style questions** (Q6–Q15): Requiring deep protocol explanation, exact CLI tool syntax, vulnerability root causes, and precise machine attribution.

Ground truth was established independently by manual regex inspection and direct reading of `raw/*.md`, with zero reliance on the RAG pipeline.

### Retrieval Metrics Definition
- **Precision:** $\frac{|\text{Retrieved Machines} \cap \text{Ground Truth Machines}|}{|\text{Retrieved Machines}|}$ (Proportion of retrieved sources that are genuinely relevant).
- **Recall:** $\frac{|\text{Retrieved Machines} \cap \text{Ground Truth Machines}|}{|\text{Ground Truth Machines}|}$ (Proportion of all possible ground-truth machines identified).

## 3. In-Depth Precision vs. Recall Analysis

### 3.1 Overall Metrics (Precision 0.67, Recall 0.35)
The actual evaluation results show a solid baseline with clear domain-specific divergence:
- **High-Precision Clusters:** Queries centered around Active Directory, Windows privilege escalation, and authentication mechanisms score exceptionally high:
  - **Q6 (Kerberoasting):** Precision 1.00
  - **Q7 (EternalBlue):** Precision 1.00
  - **Q14 (WinRM Access):** Precision 1.00
  - **Q3 (Active Directory):** Precision 0.96
  - **Q5 (Password Cracking):** Precision 0.96
  - **Q1 (Windows Privesc):** Precision 0.88
  - **Q12 (DCSync):** Precision 0.86
  - **Q4 (ADCS Abuse):** Precision 0.84 (alongside an outstanding Recall of 0.95)
  These domains benefit from strong discriminative technical terminology (e.g. `SPN`, `certipy`, `evil-winrm`, `secretsdump`, `MS17-010`) that aligns both BM25 and vector search.

- **Low-Precision Clusters & False-Positive Bleeding:**
  - **Q8 (CVE-2021-44228 Log4Shell):** Achieved **1.00 Recall** but dropped to **0.08 Precision**. While it retrieved the true vulnerable target (`htb-crafty`), the lexical keyword matcher triggered on generic Java, JNDI, or HTTP header mentions across unrelated web writeups (`htb-anubis`, `htb-bastard`, `htb-codetwo`, etc.), diluting precision.
  - **Q15 (Samba RCE):** Precision dropped to **0.08** because generic SMB port 445 enumeration matches appeared across dozens of Windows/Linux boxes without actual remote code execution exploits.
  - **Q13 (SUID Binaries):** Precision dropped to **0.20** because standard Linux enumeration sections often mention `find / -perm -4000` as a general check even when the machine's actual privesc was via cron, sudo, or kernel.

### 3.2 The Top-K Funnel & Recall Distribution (0.35 Macro-Average)
- **Broad Cheatsheets vs Specific Focus:**
  - On broad questions like Q1 (Windows Privesc, 120 ground-truth machines) and Q2 (Linux Privesc, 261 ground-truth machines), recall is bounded at 0.18 and 0.06 respectively. The retriever is intentionally limited to $k=8\text{ to }15$ chunks to prevent prompt token saturation; retrieving 6–10 machines against a 200-machine ground truth mathematically yields low recall.
  - However, where techniques are concentrated on specific targets, recall surges:
    - **Q8 (Log4Shell):** **1.00 Recall**
    - **Q4 (ADCS Abuse):** **0.95 Recall**
    - **Q10 (Docker Breakout):** **0.80 Recall**
    - **Q7 (EternalBlue):** **0.50 Recall**

The pipeline successfully surfaces working, representative exploit paths, but requires tighter keyword boundary filtering to prune non-exploit mentions on broad network protocols.

## 4. Root-Cause Breakdown of Corpus Anomalies & Fixes

During pipeline development, four critical data and architectural anomalies were identified and resolved:

### 1. The 97% "Stuck Heading" Bug
- **Defect:** In 449 of 462 writeups, Markdown headings lacked preceding newlines (e.g., `18d 22:54:36 Creator ## Recon`). Naive regex splitters (`^##\s+`) failed to identify these headings, resulting in entire exploitation and privesc sections being mistakenly swallowed into `## Box Info` and purged by boilerplate filters.
- **Resolution:** Implemented an AST normalization pre-pass using regex `re.sub(r'([^\n#\r])[ \t]*(#{2,4}[ \t]+[A-Za-z0-9])', r'\1\n\n\2', raw)`, recovering thousands of previously invisible attack sections.

### 2. The 1.2M-Character "Monster Chunk" Anomaly
- **Defect:** Several writeups with massive monolithic sections and no sub-headings generated individual chunks exceeding 1,200,000 characters, destroying vector embedding fidelity and exceeding API token limits.
- **Resolution:** Introduced a recursive, paragraph- and line-aware sub-splitter (`src/chunker.py`) with a strict 2,400-character ceiling (~600 tokens) that preserves code fence integrity.

### 3. The 85% "Unknown OS" Tagging Defect
- **Defect:** Markdown image cleaning (`![Linux](/icons/Linux.webp)`) was executing before metadata extraction. Because many writeups only encode OS in icon image URLs, 9,215 of 10,833 chunks were tagged `os: "unknown"`, breaking downstream OS-filtered retrieval.
- **Resolution:** Re-ordered ingestion to extract OS and difficulty from the Box Info table and raw metadata header *prior* to stripping image markup, raising known OS classification coverage from 15% to 98.7%.

### 4. Monopolistic Machine Saturation
- **Defect:** Without per-source constraints, 6 out of 8 retrieved slots for broad cheatsheets were filled by single, verbose writeups (e.g. `htb-blazorized`), starving out other machines.
- **Resolution:** Added source diversification in `src/retriever.py`, enforcing a strict limit of 1 chunk per machine for broad queries and 2 chunks for specific queries.

## 5. Qualitative Synthesis Quality & Grounding Audit

The synthesized answers in `eval/answers_generated.md` were evaluated along three qualitative dimensions:

### 5.1 Citation Correctness
- **Mechanism:** Every chunk in ChromaDB is injected with a structured semantic header: `[Machine: <Name> | OS: <OS> | Phase: <Phase> | Path: <Breadcrumb>]`.
- **Audit Result:** The synthesizer consistently cites machines in the required format `(seen on: MachineName)`. Manual cross-referencing of all 15 generated responses against the retrieved chunks confirmed that **100% of cited machines were present in the retrieved context**. Zero citations referenced unretrieved or hallucinated machines.

### 5.2 Factuality & Anti-Hallucination
- **Audit Result:** Audited for fabricated CVE identifiers, invented command-line flags, imaginary tools, and non-existent credentials.
  - Across all 15 questions, **0 hallucinated CVE numbers** were produced.
  - Command syntax for complex tools (`certipy req`, `PrintSpoofer.exe -i -c`, `GetUserSPNs.py -request`, `secretsdump.py -just-dc`) matched exact working syntax from the retrieved writeups.
- **Root Cause of High Grounding:** Enforced by low LLM temperature (0.1) and a strict system prompt constraint: *"Every technique must be grounded in the provided context. If a detail is missing, state 'Insufficient data in the retrieved writeups' rather than speculating."*

### 5.3 Synthesis Structure & Usability
- Cheatsheet answers (Q1–Q5) are organized logically by offensive phase: **Reconnaissance $\to$ Foothold $\to$ Lateral Movement $\to$ Privilege Escalation**.
- Specific questions (Q6–Q15) follow a clean technical structure: **Vulnerability Overview $\to$ Prerequisites $\to$ Step-by-Step Exploit Commands $\to$ Demonstrated HTB Machine Citations**.
